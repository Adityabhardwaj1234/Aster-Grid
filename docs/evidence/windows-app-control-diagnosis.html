2. The exact failure

The command used to start the backend was the console-script form: 

> uv run astergrid
error: Failed to spawn: `astergrid`
  Caused by: An Application Control policy has blocked this file. (os error 4551)

The message is produced by the process launcher before Python runs any application code. It is not an import error, a missing dependency, a port conflict, or an exception from ASTERGRID. Windows stopped the executable file itself.

3. Root cause

A Python package can declare a console entry point. Installing the package generates a small launcher executable in the virtual environment: 

backend\.venv\Scripts\astergrid.exe

That launcher is a generated, unsigned shim. On this machine an enforced Application Control policy rejects it, so uv run astergrid resolves the shim and is blocked at spawn time. The same policy can affect other generated shims such as uvicorn.exe, pytest.exe, and ruff.exe.

What this is not

This is not evidence that ASTERGRID is malicious, corrupted, or incompatible with Windows. It is a policy decision about an unsigned generated launcher. The underlying Python interpreter and the package code are allowed to run.

4. Why python -m works

uv run python -m astergrid starts the Python interpreter and asks the module system to locate astergrid/__main__.py on sys.path. The module calls the same main() function that the console script would have called. No generated .exe shim participates, so the policy has nothing to block.

The operator's equivalent command does exactly the same thing explicitly: 

uv run python -c "from astergrid.__main__ import main; main()"

Both forms are valid. The -m form is shorter and is now the documented project convention.

7. Confirming the policy (optional, read-only)

Do not weaken security

Do not disable Application Control, Smart App Control, or Defender to make a convenience shim run. Use the interpreter form documented above, or involve the machine owner or IT if an allow-list decision is genuinely required.

If the exact policy and blocked binary need to be identified, an administrator PowerShell session can read the Code Integrity operational log. This is a read-only diagnostic: 

Get-WinEvent -FilterHashtable @{
    LogName   = 'Microsoft-Windows-CodeIntegrity/Operational'
    Id        = 3077,3033,3079
    StartTime = (Get-Date).AddHours(-2)
} -MaxEvents 10 | Format-List TimeCreated, Id, Message

Relevant event identifiers are commonly described as: 3077 (blocked by enforced policy), 3033 (signing-level requirement failed), and 3079 (App Control requirement failed). The blocked file path in the event should point at the generated shim under .venv\Scripts.

Appendix A — supplied diagnosis transcript

The following is the operator-supplied analysis, reproduced for context. It is a third-party explanation, not an independent audit. Project-specific facts verified during preparation appear in sections 1–9.

Error: Failed to spawn: astergrid
Caused by: An Application Control policy has blocked this file. (os error 4551)

This is a Windows Application Control (App Control / WDAC) security-policy block, not a normal application crash.

The important part is: 

Failed to spawn: `astergrid`
Caused by: An Application Control policy has blocked this file.
(os error 4551)

It means the program attempting to launch astergrid was stopped by Windows before it could execute.

Why this happens

Windows Application Control can prevent executables from running when they don't meet the system's security policy. Common causes include:

  • Untrusted executable: Windows doesn't recognize the executable's publisher or signature.
  • Unsigned binary: The executable isn't signed with a certificate trusted by the active policy.
  • Restricted execution policy: Your Windows installation has an enforced application-control policy.
  • Build or installation issue: A newly downloaded or compiled executable isn't allowed by the policy.

How to identify the exact cause

Since you've previously encountered Windows Code Integrity blocking pip.exe on this same PC, I suspect your machine has an application-control policy actively enforcing restrictions.

Let's verify that rather than changing Windows security settings blindly.

Step 1. Open PowerShell as Administrator and run:

Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-CodeIntegrity/Operational'
    Id = 3077,3033,3079
    StartTime = (Get-Date).AddHours(-2)
} -MaxEvents 10 |
Format-List TimeCreated, Id, Message

Step 2. Look for these events:

Event IDMeaning
3077Executable explicitly blocked by enforced policy
3033Signature or signing-level requirement failed
3079File failed an App Control requirement

Microsoft documents these events in its App Control event reference.

Step 3. Send me the output.

I particularly need:

  • The blocked file's full path.
  • The policy name or policy ID.
  • The verification error, if present.
  • The process that attempted to launch it.

What I want to establish

There are two different possibilities:

  1. Astergrid-specific restriction: Only this executable is rejected. We can investigate its signature, origin and compatibility.
  2. System-wide Code Integrity restriction: Your Windows policy is preventing multiple executables from running. This would also explain your previous Python installation problems.

I don't recommend disabling Windows Application Control or weakening system security to fix this.
